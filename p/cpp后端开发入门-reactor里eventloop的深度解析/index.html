一、引言

在后端方向，无论任何语言，聊天室都是一个不可不提的环节，其中 Reactor 是现代服务器高并发访问的核心知识点之一。

坦白来说，这个项目是我从 AI 那儿掏出来的半成品，所以用博客来吃透这玩意儿是个不错的选择（PS：配置这玩意老费劲了）。

那话不多说，在读者阅读前，有以下几点注意：

Q：这篇文章写给谁？ A：刚接触后端知识的读者，希望帮助他们更好地理解与掌握。

Q：为什么要写 EventLoop？ A：在聊天室里，main 接下来调用的基本上就是 EventLoop；而 Reactor 里的 EventLoop，更是整个架构的核心。

Q：如何一句话总结 EventLoop？ A：它是整个 Reactor 架构的核心，一种基于“一线程一循环”的设计，以少量线程来高效处理大量请求

二、大纲

2.1 本文结构

EventLoop 可以分为三大部分：loop 循环、定时器管理、fd 事件管理。本文会按照这三个部分逐一分析。

1. loop 循环 包括 loop()、quit()、isInLoopThread()、assertInLoopThread()、runInLoop()、queueInLoop()。

2. 定时器管理 包括 TimerEntry 结构体、runAfter()、processTimers()、nextTimeoutMs()。

3. fd 事件管理 包括 addFd()、modFd()、delFd()、hasFd()。

补充说明：项目中 start() 方法出现在多个类里（TcpServer、Connection、EventLoopThread 等），此处只做简单介绍，后续会专开一篇讲解。

2.2 你需要知道的前置知识点

  • 一线程一循环（One Loop Per Thread）
  • Epoll 基础（ET 模式、EPOLLIN、EPOLLOUT）
  • 非阻塞 IO 与 EAGAIN

EventLoop::EventLoop() {
    m_threadId = std::this_thread::get_id();

    m_epollFd = ::epoll_create1(EPOLL_CLOEXEC);
    if (m_epollFd < 0) abort();

    m_wakeupFd = ::eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
    if (m_wakeupFd < 0) abort();

    addFd(m_wakeupFd, EPOLLIN, [this](uint32_t) { drainWakeup(); });
}

这 8 行代码做了四件事：

  1. 记录当前线程 id（m_threadId）
  2. 创建 epoll 实例（m_epollFd）
  3. 创建 eventfd（m_wakeupFd）
  4. 把 m_wakeupFd 挂到 m_epollFd 上

3.1.2 设计决策与对比

Q：为什么用 epoll_create1 而不是 epoll_create？

epoll_create 是旧版，它的 size 参数在新内核中已被忽略，但仍要求大于 0，容易误导使用者。

epoll_create1 支持 EPOLL_CLOEXEC，可以一次性完成 epoll 实例化以及 CLOEXEC 标记，避免 fd 随 exec() 泄漏。另外，flags 按位设计，方便后续功能扩展。

Q：为什么用 eventfd 而不是 pipe 做跨线程唤醒？

· pipe 占两个 fd（读端 + 写端），eventfd 只占一个。 · pipe 是字节流，多次 write 可能对应多次 read，需要循环读到 EAGAIN；eventfd 是 64 位无符号计数器，多次 write 累加，一次 read 清零，不存在部分读。 · eventfd 挂到 epoll 上只监听 EPOLLIN，读逻辑极简；pipe 要处理读端/写端关闭的复杂边界。

Q：为什么创建失败直接 abort()，不抛异常？

abort() 是强制终止进程，返回 SIGABRT。

EventLoop 是服务器的“心脏”。epoll 都创建失败，说明系统资源已经严重不足。与其带着一个坏掉的 EventLoop 继续跑，在后面某个不可预期的地方崩溃，不如当场暴毙，死得明白。

3.1.3 该环节总结

构造函数虽然只有 8 行，但它奠定了整个 EventLoop 的基调：

· 线程绑定：m_threadId 决定了后续所有 epoll 操作必须在本线程内完成。 · 事件循环的物理基础：m_epollFd 是监听中心，m_wakeupFd 是唯一的“后门”。 · 唤醒机制提前就位：eventfd 在构造时就被挂到了 epoll 上，说明跨线程唤醒不是“附加功能”，而是 EventLoop 的一等公民。

void EventLoop::loop() {
    m_threadId = std::this_thread::get_id();
    std::vector<epoll_event> events(kInitialEventListSize);

    while (!m_quit.load()) {
        const int timeout = nextTimeoutMs();
        const int n = ::epoll_wait(m_epollFd, events.data(), events.size(), timeout);
        if (n < 0) {
            if (errno == EINTR) continue;
            break;
        }

        for (int i = 0; i < n; ++i) {
            const int fd = events[i].data.fd;
            const uint32_t ev = events[i].events;

            auto it = m_handlers.find(fd);
            if (it == m_handlers.end()) continue;
            EventHandler handler = it->second;
            handler(ev);
        }

        processTimers();
        doPendingTasks();
    }
}

loop 是 EventLoop 的核心，靠 while 循环不断运转。每一圈五步走：准备 events 数组，算超时时间并传给 epoll_wait 等事件，遍历就绪事件执行回调，处理到期定时器，处理跨线程投递的任务。

3.2.2 设计分析与对比

① Q:为什么要拷贝handle A:不能直接 it->second(ev)。因为回调内部可能调用 delFd()，而 delFd() 会从 m_handlers 里删除这个 fd 对应的条目。如果你手里还攥着迭代器 it，删完之后 it 就失效了。回调执行完之后，如果你再碰 it，就是访问已经释放的内存，直接崩。拷贝一份到局部变量，回调怎么折腾 m_handlers 都不影响你手里这份副本。

②Q:为什么要处理EINTR A:epoll_wait 返回负数时，要区分两种情况： · errno == EINTR：系统调用被信号打断了。这不是错误，只是“我还没等到事件就被一个信号叫醒了”。重新调 epoll_wait 就行，所以 continue。 · 其他 errno：真正的错误（比如 m_epollFd 被关了），没法继续，break 退出循环。

③ 为什么把两个函数放在后面 因为 IO 事件的优先级最高。先把网络数据读走、发走，再处理定时器和跨线程任务。如果反过来，定时器回调里如果做了耗时操作（比如写数据库），会阻塞后面的 IO 事件分发，导致网络延迟飙升。

3.3 跨线程唤醒

3.3.1 核心源码

  1. runInLoop()：分流。在 loop 线程就直行，否则入队。
  2. queueInLoop()：加锁塞任务，然后调 wakeup()。
  3. wakeup()：往 eventfd 写一个整数。
  4. drainWakeup()：读到 EAGAIN，清空计数器。
  5. doPendingTasks()：swap 任务队列到局部变量，锁外执行。

注: doPendingTasks里使用swap，一方面是避免死锁，另一方面是只锁住一行代码，避免影响效率

3.4 定时器管理：分离-交换-执行

3.4.1 设计函数及作用

nowMs() 获取单调时间戳 runAfter() 注册定时器，记录绝对过期时间 nextTimeoutMs() 算最近定时器还有多久到期，作为 epoll_wait 超时 processTimers() 把到期的挑出来执行，分离-交换-执行

3.5 fd 事件管理

addFd、modFd、delFd 是对 epoll_ctl 的薄封装：addFd 把 fd 挂到 epoll 上并登记回调，modFd 用于动态修改监听事件（比如写缓冲满时加 EPOLLOUT），delFd 从 epoll 摘除并删除回调。三者都必须在 loop 线程内执行，靠 assertInLoopThread() 兜底。

一句话总结：这个模块没什么设计决策，就是个 epoll 操作的工具层。

四、知识点衍生

4.1 线程封闭（Thread Confinement）

线程封闭的核心思想是“通过限制数据只在单线程内访问，来完全规避并发加锁的开销”。它主要分为三类：栈封闭（局部变量）、ThreadLocal封闭（线程独立副本）以及专属线程封闭（Ad-hoc Thread Confinement）。

我的项目中的 One Loop Per Thread 模型，严格来说属于“专属线程封闭”。每个 IO 线程独占一个 EventLoop，负责管理一批固定的 Connection。因为连接从建立、读写到销毁，全部都在其绑定的那个线程里闭环完成，所以 Connection 内部的读写缓冲区、解析状态机等数据，天然就没有数据竞争，完美实现了无锁化高并发。

4.2 无锁化高并发

无锁化高并发其实本质上是为了通过减少共享来减小开销，其中用的最多的就是线程共享(比如专属线程封闭，在这个项目里面是非常典型的)，原子操作及数据结构优化等等，而最常用的方法有两个第一个是在架构层面的减小共享，也是目前使用最多的，核心思想是“我不共享，我就不用锁”，第二个是使用数据结构里的硬件原子操作，不过实现起来太麻烦，并且会带来复杂度的急剧上升，就一笔带过

4.3 悬垂指针：ai造成的低级失误

4.3.1 问题发现

在阅读源码时，在最后的start()函数里面，发现m_loop一直拿着loop的指针，而loop在子线程结束后销毁，导致悬垂指针

4.3.2 怎么修（unique_ptr 或成员变量）

把 EventLoop 从栈上搬到堆上，或者作为 EventLoopThread 的成员变量，让它的生命周期和线程绑定。

五、总结

5.1 收获浅谈

啃透 EventLoop 的过程，要真正理解了 Reactor 架构的“心脏”是怎么跳动的：

· 一线程一循环：每个 IO 线程独立持有 epoll，连接绑定线程后无需加锁。 · eventfd 跨线程唤醒：其他线程通过 write 唤醒阻塞的 epoll_wait，这是主从 Reactor 协作的基础。 · swap 锁外执行：doPendingTasks 把任务队列 swap 到局部变量，锁外执行，避免死锁、缩短临界区。 · 悬垂指针：EventLoopThread::start() 里的栈变量 EventLoop loop 让我踩了 Use-After-Free 的坑，后来用 unique_ptr 修复。
