一.引言

如果说上一把的 EventLoop 是主从 Reactor 的心脏，那接下来出场的这位，就是身处网络层却心系业务层，主从 Reactor 的超绝骨架——TcpServer。

它真正做到了“站中间串两边”：

· 向上：接业务层。把收到的数据通过回调扔给上层的 ChatServer。 · 向下：接操作系统。摆弄 socket、bind、listen，调戏 epoll。 · 对内：还能“搞一群小弟”。也就是维护着由多个 EventLoopThread 组成的 IO 线程池，替它把接到的请求分发给各个子线程去干。

它没有 EventLoop 那么极客硬核，但如果没有这个骨架，这个系统就会直接张口闭眼，宛如奖励了自己一个月以后虚弱不堪

二、大纲

1. 开业准备（向下接系统） 首先调用 start() 函数，里面的 createListenSocket() 负责创建监听套接字。之后启动 IO 线程池，调用主线程的 mainLoop，把 listenFd 和读事件注册到主线程的 epoll 里。

2. 客户到来（迎宾与分发） 如果有客户访问，listenFd 触发，调用 handleAccept() 去循环 accept 拿到客户端 fd。之后通过 pickLoop() 进行原子轮询（Round-Robin）寻找子线程，找到后由 dispatchToLoop() 把这个 fd 注册到目标子线程的 epoll 中。

3. 发送消息（向上接业务） 当业务层需要群发消息时，调用 forEachConnection()。核心在于锁内拷贝快照，锁外执行发送，以此来避免网络阻塞导致死锁。

4. 断开连接（资源回收） 调用 removeConnection() 上锁并从 m_connections 集合中移除。配合 shared_ptr 智能指针，当引用计数归零时，自动触发 Connection 析构，底层自动 close(fd) 释放资源。

三.核心操作

3.1 初始化

3.1.1 核心源码

int TcpServer::createListenSocket() { const int fd = ::socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK | SOCK_CLOEXEC, 0);

int opt = 1;
::setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
::setsockopt(fd, SOL_SOCKET, SO_REUSEPORT, &opt, sizeof(opt));

sockaddr_in addr;
memset(&addr, 0, sizeof(addr));
addr.sin_family = AF_INET;
::inet_pton(AF_INET, m_bindAddr.c_str(), &addr.sin_addr);
addr.sin_port = htons(static_cast<uint16_t>(m_port));

::bind(fd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr));

::listen(fd, SOMAXCONN);

return fd;

}

3.1.1 体系作用：为什么它是地基？

如果把服务器比作一家餐厅，createListenSocket 就是去工商局注册门牌号，并在门口挂上营业牌。没有它，你的 EventLoop 和线程池配得再花哨，内核也根本不知道该怎么帮你接收连接。 在这里，socket() 的第三个参数直接传入了 SOCK_NONBLOCK 和 SOCK_CLOEXEC。前者直接省去了后续调用 fcntl 设置非阻塞的额外系统调用开销；后者（exec 时关闭）则是为了防止这个监听 fd 泄漏给 fork 出来的子进程。

3.1.2 opt 的作用与 setsockopt 的局限

为什么 setsockopt 里面一定要传 &opt？因为它的第四个参数是 const void*。系统为了兼容各种选项（整数、结构体、字符串），只接收“内存地址 + 长度（sizeof(opt)）”。你传一个变量 opt = 1 的地址过去，系统才能顺着地址去读取那个 4 字节的配置。

· 局限性：setsockopt 并非全能。比如 SO_REUSEPORT 虽然允许多个 socket 绑同一端口，但内核到底把新连接分给哪个 socket 是不可控的。而且这行代码只负责配置，即使设置了复用，如果遇到系统级权限锁定，bind 依然会失败。

3.1.3 sockaddr_in：组装地址与致命坑点

在调用 bind 之前，必须把 IP 和端口填进 sockaddr_in 结构体。这里有三个新手的“死亡坑点”：

  1. 必须 memset 清零：这个结构体有一个历史遗留的 sin_zero（填充字段）。如果不把整个结构体清零，残留的随机垃圾内存会导致 bind 失败，报 EINVAL 错误。
  2. inet_pton：把人类可读的字符串（如 “0.0.0.0”）转成网络传输用的二进制数。
  3. htons 字节序转换：主机通常是小端序，而网络协议栈必须是大端序。如果不转，你监听 8888，别人得去连 57005 才能连上。

补充：最后的 listen(fd, SOMAXCONN) 极其重要，SOMAXCONN 是指全连接队列（已完成三次握手，等待 accept 的连接）的最大长度。不设置的话，高并发下队列一满，系统就会拒绝新连接。

3.2 有人访问

补充:在这之前会有一个start函数，主要是检查系统状态，获取底层网络句柄，创建n个子进程，主线程循环检测这四个步骤

当主线程的 epoll_wait 监听到新连接，整个“接客与分发”的流水线正式启动。这条流水线主要由三个函数接力完成：

🎯 第一棒：handleAccept()（主线程/迎宾员）

这是最核心的入口。一进来，它直接进入 while(true) 循环。

  1. 接客：调用 accept4() 拿到内核分配的新 client_fd。如果返回 -1 且 errno == EAGAIN，说明本次连接已经接完，break 退出循环（这是 ET 模式的基操）。
  2. 限流防御：拿到 fd 后，检查当前连接数 connectionCount() >= MAX_CONNECTIONS。如果服务器快撑爆了，直接 close(fd) 拒绝接入。
  3. 信息提取：用 inet_ntop 和 ntohs 把内核里的二进制 IP 和端口，拼装成 “127.0.0.1:8888” 这种人类可读的字符串 peerStr。
  4. 交棒：把拿到的 fd 和 peerStr 传给下一个函数 dispatchToLoop。

🎯 第二棒：pickLoop()（轮询器）

dispatchToLoop 进来第一件事，就是得找个干活的小弟。

  1. 原子轮询：pickLoop 内部调用 m_nextLoop.fetch_add(1) % m_loops.size()。
  2. 负载均衡：每次来个新连接，原子计数器加 1，然后取模。这样就能把连接均匀地分给 io-0、io-1、io-2 等各个子线程的 EventLoop，绝对不会出现“累死一个，闲死一堆”的情况。

🎯 第三棒：dispatchToLoop()（跨线程投递员）

拿到了 loop（子线程），现在要把 fd 安全地送过去。

  1. 为什么要用 runInLoop？ 因为 fd 最终要挂到子线程的 epoll 上（addFd），而 epoll_ctl 是不允许跨线程操作的（会触发 assertInLoopThread 崩溃）。
  2. 投递任务：把“创建 Connection 对象、挂载 fd、塞进连接池”这一系列动作打包成一个 lambda 任务，扔进子线程的 runInLoop 队列。
  3. 唤醒：子线程的 eventfd 被写入，子线程醒来，在自己的线程里执行这个 lambda，连接正式安家。

void TcpServer::forEachConnection(
    const std::function<void(const std::shared_ptr<Connection>&)>& fn) const {
    if (!fn) return;
    std::vector<std::shared_ptr<Connection>> snapshot;
    {
        std::lock_guard<std::mutex> lk(m_connMutex);
        snapshot.assign(m_connections.begin(), m_connections.end());
    }
    for (const auto& c : snapshot) {
        if (c && !c->closed()) fn(c);
    }
}

1. 为什么不能直接遍历 m_connections，非要搞个 snapshot（快照）？

· 迭代器失效：假设你正在遍历 m_connections 发消息，突然有个玩家网络断开，另一个线程调用了 removeConnection，把这个连接从 m_connections 里 erase 了。此时你手里的迭代器瞬间悬空，程序直接崩溃（Segmentation fault）。 · 解法：在锁内拷贝一份名单（snapshot），然后在锁外遍历快照。就算原集合被删光了，快照里的 shared_ptr 依然能保证这些对象的生命周期不会在遍历时爆炸。

2. 为什么必须在锁外发消息？

· 死锁与性能雪崩：发送网络数据（send）是极其耗时的操作（可能遇到网卡拥塞、TCP 滑动窗口满了等）。如果你拿着 m_connMutex 去发消息，只要有一个玩家网卡了，这把锁就会一直不释放。其他想登录、想退出的玩家全得死等，服务器直接卡死。 · 解法：锁内只拷贝，锁外去发送。

3. 为什么遍历时要判断 c && !c->closed()？

· 可能在拷贝快照到你真正发消息的这零点几毫秒内，某个客户端恰好断开了。所以发之前必须防一手，检查连接是否还活着。

void TcpServer::removeConnection(const std::shared_ptr<Connection>& conn) {
    if (!conn) return;

    {
        std::lock_guard<std::mutex> lk(m_connMutex);
        m_connections.erase(conn);
    }

    // 若当前不在连接所属的 loop 线程（例如被其它线程强制关闭），
    // 就把"释放最后一个引用"的动作投递到它的 loop 线程，保证对象在线程内析构。
    EventLoop* loop = conn->loop();
    if (loop && !loop->isInLoopThread()) {
        std::weak_ptr<Connection> weak = conn;
        loop->runInLoop([weak]() {
            if (auto self = weak.lock()) {
                // 任务结束后 self 析构，真正释放
            }
        });
    }
}

第一问：为什么要投递给 loop->runInLoop？

因为 Connection 对象内部管理着 epoll 的事件（m_epollFd）、读写缓冲区。跨线程去 close(fd) 或者释放这些资源，会引发极其严重的竞态条件。必须让它在自己所属的 IO 线程里，安安静静地“寿终正寝”。

第二问：为什么 lambda 里面不直接捕获 shared_ptr，而是捕获 weak_ptr？

· 如果你捕获 shared_ptr：runInLoop 会把这个任务塞进队列。如果这个任务一直没被调度，队列里就永远存着一个 shared_ptr，导致这个 Connection 对象永远无法被释放（这就叫内存泄漏）。 · 捕获 weak_ptr：它不会增加引用计数。如果这期间，所有的业务逻辑都放弃了这个连接（引用计数归零），Connection 提前析构了，weak.lock() 就会返回空指针，任务直接安全退出。如果没析构，lock() 成功，任务执行完，self 销毁，才真正触发最后一次析构。

第三问：为什么在原线程里（如果满足 isInLoopThread）就不需要这么绕？

因为如果当前就在 IO 线程，直接让 shared_ptr 离开作用域，析构函数立刻执行，安全且高效，没必要多此一举（任务队列是有系统调用开销的）。

第四部分 拓展知识点

拓展点 ① 原子轮询

1

源码
const size_t idx = m_nextLoop.fetch_add(1) % m_loops.size();
  1. 为什么要轮询？ 因为主从 Reactor 模型中，主线程 accept 后必须把连接分给子线程。如果不轮询，一直给 0 号线程，0 号线程会被累死，其他线程在“摸鱼”，这叫负载不均衡。
  2. 为什么用 std::atomic 而不是 std::mutex？ · 如果加锁（lock_guard），每次来一个新连接，主线程都要去抢锁、改数据、放锁。虽然锁的时间极短，但在十万级并发下，频繁的加锁解锁会导致严重的内核上下文切换和 CPU 缓存失效。 · std::atomic 底层利用了 CPU 的硬件原子指令（比如 CAS - Compare and Swap），或者直接锁住总线/缓存行。它把并发控制交给了硬件，完全在用户态完成，没有系统调用，没有上下文切换。 · fetch_add(1) 保证了在多线程环境下，每次自增 1 绝对安全，最终通过 % m_loops.size() 实现完美的轮询分发。这在 C++ 后端里是教科书级别的“无锁化编程”。

拓展点 ② 智能指针

  1. unique_ptr（独占所有权）： · 用在 m_ioThreads 里。因为一个 EventLoopThread 只能属于 TcpServer 一个人，绝对不允许别人拷贝或者共享。unique_ptr 保证了只要 TcpServer 挂了，这些 IO 线程一定会被安全析构。
  2. shared_ptr（共享所有权）： · 用在 m_connections 里。因为一个 Connection 不仅在连接池里有一份引用，可能业务层（比如 ChatRoom 发送广播时）也临时拿着它的指针。shared_ptr 内部的引用计数保证了：只要还有任何一个地方在用它，它就绝对不会被销毁；等大家都不用了，引用计数归零，它自动 close(fd) 并释放内存。
  3. weak_ptr（只观望不拥有）： · 用在跨线程销毁（removeConnection 里的那个 lambda 捕获）。weak_ptr 不增加引用计数，它是用来打破循环引用和安全探测的。在跨线程投递任务时，用 weak_ptr.lock() 判断对象是否还活着。活着就转成 shared_ptr 安全操作，死了就跳过，完美避免了野指针崩溃。

五.总结
